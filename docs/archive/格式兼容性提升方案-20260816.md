# Sensend 格式兼容性提升方案

> 日期：2026-08-16
> 范围：入向（外部内容复制进 Sensend）+ 出向（分发到 Notion / FlowUs / 飞书 / 本地 .md）的格式保真与规范化
> 原则：不改产品形态、不做双向同步；单一真源、减法优先；每阶段可独立验收、build 通过
> 状态：待审阅（仅方案，未动代码）

---

## 一、目标

一句话：**同一份笔记，在 Sensend 里长什么样，发出去就应该长什么样（或以明确的、一致的降级规则呈现），且四个出口的保真度对齐。**

衡量标准：

1. 格式能力矩阵四条链路对齐，降级处显式、有测试、有文档；
2. 转换逻辑收敛为可单测的纯函数，杜绝四处复制粘贴的平行实现；
3. 不引入新框架、新依赖（纯 Rust 内部重构 + 测试），转换耗时无感知（现为微秒级，保持）。

### 2.3 入向（粘贴）现状

- HTML 粘贴：交给 TipTap 默认解析（TableKit 已注册，表格可进）——链路健康，但未验证过微信/Word 等脏 HTML 场景；

## 三、总体设计：统一转换核心（唯一架构级改动）

### 3.1 问题本质

现在每个适配器各自遍历 TipTap JSON 树、各自实现"节点识别 + 内联 mark 映射"，导致：同一缺陷要修四遍（且事实证明没修齐）；新平台接入成本高；无法集中测试。

### 3.2 推荐方案：IR 中间层（Normalization → Mapping 两段式）

```
TipTap JSON
    │
    ▼  adapters/convert.rs（唯一遍历点，纯函数）
规范化 IR：Vec<IrBlock>
    │   （块级：Paragraph/Heading(n)/Bullet{depth}/Ordered{depth}/Todo/
    │     Quote/Code{lang}/Divider/Table/…；内联：Vec<Inline>，
    │     Inline = Text{content, marks} | Break，一次性解决 hardBreak）
    ▼
┌─────────┬─────────┬─────────┬─────────┐
│ notion  │ flowus  │  lark   │  local  │   ← 每家只剩薄映射层
│ ir→块API │ ir→块API │ ir→块API │ ir→md  │     （无遍历、无递归）
└─────────┴─────────┴─────────┴─────────┘
```

要点：

1. **normalize 一处做三件事**：拍平/降级决策全部前置（如"飞书表格降级"变成 lark 映射层里一条显式规则）；hardBreak 归一为 `Inline::Break`；列表项的"首段+后续段+子列表"结构保留在 IR 里，不再丢失信息。
2. **能力矩阵以代码为真源**：每个映射层导出 `fn capabilities() -> &'static [Capability]`（或用编译期常量表），矩阵文档从它生成，杜绝文档滞后（项目已有 CODE-WIKI 滞后的前科）。
3. **纯函数 + cargo test**：normalize 和四个 mapper 全部无 IO、无网络，可直接用 fixture JSON 做黄金文件测试——这是本项目目前完全缺失的测试形态。
4. **减法核算**：现有 notion.rs + flowus.rs 转换部分约 400 行重复，IR 核心 + 内联归一约 200 行，四个薄映射层各 60-80 行，**净代码量下降**，且彻底消灭缺陷 #8。

### 3.3 备选方案：共享工具库（不动结构）

仅抽取 `collect_text_nodes` / 表格提取等公共函数为 `adapters/inline.rs` 共享，各适配器仍自行遍历。改动小、风险低，但嵌套列表、hardBreak 这类"结构级"差异仍散落各处，治标不治本。

**结论：推荐 3.2。** 它与"单一真源"原则同构，且是唯一能让能力矩阵"活"起来的路线。若希望风险最小，可先按 3.3 落地缺陷修复（阶段一），再择机做 3.2——两条路线的阶段划分见第七节。

## 五、入向（粘贴）规范化方案

定位：Sensend 是速记工具，入向策略应是**"宽容接收、规范存储"**——进入编辑器的内容立即被规范化为 TipTap 标准节点，出口才能四路对齐。

1. **粘贴验证清单**（先行，无代码改动）：微信文章、Word、网页、VS Code、Obsidian 五类来源 × 富文本/纯文本/Markdown 三形态，形成用例库，作为后续修复的验收基准；
2. **Markdown 粘贴补齐**：验证 `@tiptap/markdown` 对 GFM 表格、任务列表的解析；缺表格则在其 parse 后补一步轻量后处理（或将 taskList 粘贴映射为普通列表并记入矩阵）；
3. **脏 HTML 降噪**：确认 TipTap 默认解析已丢弃 font/color/背景等样式类属性（预期已丢，验证即可）；不引入 sanitizer 依赖；
4. **显式边界**：图片粘贴当前静默丢弃——建议在矩阵与 README 明示"纯文本速记工具，不含图片"，让预期对齐，而非留一个隐形坑。

## 六、测试与验收

1. **测试设施**：`src-tauri/tests/`（或模块内 `#[cfg(test)]`）+ `fixtures/` 目录存放代表性 TipTap JSON（嵌套列表、表格+内联、hardBreak、待办、代码块、超长标题等 8-10 个黄金用例）；
2. **每个映射层对每个 fixture 断言输出**：新增格式 → 加 fixture → 四家映射层强制表态（支持/降级/拒绝），矩阵自动保持真实；
3. **验证链**：`cargo test` + `cargo check`（注意 MSVC 环境需按 HANDOVER 手动激活）+ `npm run build`；真机走查每平台各发一条含全格式的样例笔记。

## 八、其他专业建议（与格式链路无直接耦合，按价值排序）

1. **note.md 名实不符**：内部文件实为 TipTap JSON，建议改名 `note.json` + 一次性迁移（读旧写新），消除"打开数据目录看到假 Markdown"的困惑；
2. **错误文案双轨制**：前端 `friendlyError` 与适配器内 `friendly_error` 规范并存，建议收敛到适配器层（错误最了解上下文），前端只做兜底展示；
3. **暂缓但值得记录**：多目标同时分发（一次 @多个平台，架构上只是 publish 循环 + 汇总 toast，改造成本低）、发送历史/离线补发（改变产品形态，明确不做）；飞书 token、各平台密钥明文存 config.json（桌面单机可接受，留意即可）；
4. **文档纪律**：adapter-development-guide.md 第 5 节的"必须支持"清单与实际能力矩阵已经脱节，本方案落地后以代码生成的矩阵为准，指南只写"如何写适配器"，不再罗列能力。

## 九、明确不做（减法声明）

双向同步、增量更新已发内容、离线队列、图片/附件支持、新增平台适配器、编辑器功能扩展（除下述一项外）。唯一例外建议：**注册 TaskList 扩展**——四个适配器的待办转换分支已全部写好，只差编辑器入口（约 5 行配置），属于"付费已毕、只待领取"的能力，且待办是速记场景高频格式；若不采纳，则应删除四处的死分支，二选一，不留悬空代码。
