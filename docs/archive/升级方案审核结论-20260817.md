## 三、必须修正的执行细节（4 项，不修正会翻车）

### 3.1 ❌ mention 检测优化代码是错的（升级方案 4.3）

方案给出的：

```ts
if (tr.docChanged && tr.steps.some(s => s.toJSON().stepType !== 'replace')) { ... }
```

**问题**：打字插入、退格删除全都是 ProseMirror 的 `ReplaceStep`（插入 = from==to 的 ReplaceStep）。按此条件，恰好**跳过**了唯一需要检测的场景——插入/删除 mention。这段代码等于把检测完全关掉，mention 联动会静默失效（底栏不再同步），是典型的新 bug。

**正确做法**（利用项目里已有的 `mentionReplace` meta，[useEditor.ts L74/L181](sensend/src/composables/useEditor.ts#L74) 已在写）：

```ts
onUpdate: ({ editor: e, transaction: tr }) => {
  // ...
  if (onMentionChange) {
    // 快路径1：本事务是 mention 替换（setMention / suggestion.command 打的标记）
    // 快路径2：上次没 mention 且本次没删过字符 → 不可能有 mention（@ 触发只新增 mention，靠快路径1捕获）
    const isMentionReplace = tr.getMeta('mentionReplace') === true
    const deletedSomething = tr.steps.some(s => (s as any).from !== (s as any).to)
    if (isMentionReplace || deletedSomething || lastMentionId !== null) {
      // 只有这三种情况才值得全量遍历
      let currentMentionId: string | null = null
      e.state.doc.descendants((node: any) => {
        if (node.type.name === 'mention' && node.attrs.id) currentMentionId = node.attrs.id
      })
      if (currentMentionId !== lastMentionId) {
        lastMentionId = currentMentionId
        onMentionChange(currentMentionId)
      }
    }
  }
}
```

说明：普通打字（from==to 的纯插入且非 mention 替换且当前无 mention）直接跳过遍历，覆盖 99% 按键；删除动作和存在 mention 时保守回退到全遍历（速记文档很小，遍历本身 <0.5ms，不是瓶颈）。**宁可少优化，不可错优化。**

### 3.2 ❌ vite manualChunks 单独无效（升级方案 4.2）

`manualChunks` 只是把代码切到另一个文件，**静态 import 依然会在启动时加载它**，主窗口 JS 解析量一点没少。正确做法二选一：

- **推荐**：[main.ts](sensend/src/main.ts) 改动态导入，Rollup 自动分包，manualChunks 可以不要：

```ts
if (page === 'config') {
  import('./ConfigWindow.vue').then(({ default: ConfigWindow }) => {
    createApp(ConfigWindow).mount('#app')
  })
} else {
  const { default: App } = await import('./App.vue')
  createApp(App).mount('#app')
}
```

- 或保守版：仅把 ConfigWindow 动态化，主窗口路径不动。

验收时用 `npm run build` 后检查 dist 产物：config 相关 JS 必须是独立 chunk 且主 chunk 不包含 ConfigWindow 字符串。

### 3.3 ❌ visible:false + 前端 show() 缺权限（升级方案 4.2）

前端调 `getCurrentWindow().show()` 需要 capability 授权。当前 [capabilities/default.json](sensend/src-tauri/capabilities/default.json) 只有 `core:window:allow-start-dragging` 和 `allow-set-always-on-top`。**必须补：**

```json
"core:window:allow-show"
```

否则白屏优化上线即报权限错误。同理悬浮球窗口要用的 API（见 3.4）。

### 3.4 ❌ 悬浮球窗口的三个硬性前置（升级方案第五节）

1. **capabilities 的 windows 数组**必须加新窗口 label（如 `"ball"`），否则该窗口内任何 window API 都无权限。
2. **联动必须收口到 Rust 侧统一入口**。现在"唤起主窗"的代码散在四处：[lib.rs L17-20](sensend/src-tauri/src/lib.rs#L16-L21)（single-instance）、L67-71（托盘菜单）、L79-87（托盘点击）、hotkey.rs（快捷键）。若前端各自为政，托盘点一下、球不消失。建议 Rust 侧封装 `show_main()`：show main + hide ball 一把梭，四处调用点全部换掉。
3. **内存预算自相矛盾**：方案 4.7 要求空闲 <80MB，5.4 又要求悬浮球独立 WebView——Windows 上每个 WebView2 实例多吃 30-60MB，两个预算不能同时成立。二选一：
   - 悬浮球窗口**懒创建**（用户第一次隐藏主窗时才 build），常驻后预算放宽到 <130MB；
   - 或维持 80MB 目标，悬浮球不用独立窗口（不推荐，动画会被主窗渲染挤）。
   建议前者，并把 4.7 的验收数字同步改为「主窗独处 <80MB / 球+主窗 <130MB」。

## 四、建议补充的执行细节（8 项）

### 4.1 Notion/FlowUs children 嵌套：单次请求只有 2 层

方案 3.4-#2 说"list item 携带 children 字段表达真嵌套（创建时即可带）"——方向对，但 Notion 的 append/create children API **单次请求嵌套最多 2 层**，方案风险表写的"限制最大嵌套 3 层"会被 API 打回。执行时按此实现：
- ≤2 层：单请求携带 children；
- 第 3 层：单独追加请求（拿到父 block id 后再 PATCH）；
- 为省事可直接把降级阈值定为 2 层（速记场景 3 层嵌套极罕见），写入能力矩阵即可。
FlowUs 的 API 是 Notion 兼容风格但**是否接受嵌套 children 未实测**，P0-B 真机走查时先发一条两层嵌套笔记验证，不行就整体拍平降级（保文本不丢）。

### 4.2 飞书待办：先验证 block_type 17

飞书 docx API 存在 todo 块（block_type=17，带 checked 样式），方案 #10 的"伪待办"大概率可转正。但 style 字段结构需以官方文档为准，实现时先 curl 一条真实请求验证，成功再删 `[x] ` 前缀方案。失败则保留前缀并写入能力矩阵，**别留悬空代码**（方案自己说的，赞成）。

### 4.3 "✓ 已发送"标记：不要写进文档

若给 mention 节点加 `sent: true` attr，会触发自动保存、污染 note.json、下次启动还在——与"2s 消失"的产品意图矛盾。正确实现是 ProseMirror **decoration**（editor plugin 层的临时装饰，不碰文档 JSON），发送成功后挂 2s 自动卸掉。

### 4.4 note.md → note.json 迁移：不删旧文件

迁移逻辑：读优先 note.json，无则读 note.md；下次保存一律写 note.json。**旧 note.md 保留不删**（或改名 .bak）——符合"防止数据丢失"红线，一行删除代码都不要写。版本 N+1 再考虑清理。

### 4.5 主题的跨窗口同步

主窗、配置窗、悬浮球是三个 WebView，`data-theme` 各自独立。主题选择建议走后端（参照 default_target 先例：`set_theme` 命令写 config.json + emit `theme-updated` 事件，三窗口监听），别用 localStorage（配置窗是动态创建的窗口，同源虽共享但时序上不可靠）。另：暗夜主题 accent 建议 `#4ecca3` 改为品牌绿系暗色变体（品牌是 `#2CAF68`），保持品牌一致性。

### 4.6 黄金测试要分两层断言

P0-A 的 fixtures 会把**现状缺陷输出**（如飞书 language:1）也快照进去。执行时每个 fixture 断言分两个文件：
- `expected_current.md`（锁现状，IR 重构期间防回归）
- `expected_target.md`（修完对应缺陷后切换断言目标）

否则 IR 落地时会把"修好的输出"误判为回归，或把"缺陷输出"当正确基线焊死。

### 4.7 MSVC 构建入口更正

方案风险表写"按 HANDOVER 手动激活环境"——**更正为唯一可靠入口**：

```powershell
cd F:\fzz-Project\sensend\sensend
powershell -NoProfile -ExecutionPolicy Bypass -File "scripts\build-release.ps1"
```

（Rust/VS Build Tools 均装在 M 盘非 PATH 位置，普通终端直接 cargo 必失败。详见 `sensend/BUILD-ENV.md`。）CI/验证链里的 `cargo test` 同样要在该环境跑，建议脚本加一个 `-Test` 开关。

- **别动 `sensend-release/`**：那是 0.2.0 时代的旧副本，本次升级所有改动只进 `sensend/`，改错目录等于白干。
