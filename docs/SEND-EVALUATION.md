# Sensend 发送质量评估报告

> 版本：v0.4.0 ｜ 评估日期：2026-08-18
> 评估范围：IR 出站格式保真度 + 发送链路速度与稳定性
> 实证基线：`cargo test` 72 个测试全部通过（0 失败）

---

## 一、评估方法

本报告从两个维度审视 Sensend 的发送质量：

**格式规范性**——编辑器内容经 IR 中间层转换后，到达各平台时是否保留了用户输入的格式意图。逐平台对照 API 规范与代码实现，交叉核对代码、测试、格式调研文档三方。

**发送速度与稳定性**——从用户按下发送到内容落盘的全链路，分析时序开销、已有防御机制、尚未覆盖的风险点。

测试覆盖：IR 层 13 个边界测试（尾部空段剥除、嵌套列表、表格行内格式、mention 保护等），四平台黄金快照共 44 个，加目标断言测试合计 75 个（分项：Markdown 11+2、Notion 11+6、FlowUs 11+4、飞书 11+6、IR 13）。

---

## 二、格式规范性评估

### 2.1 架构保障

IR（中间表示）是出站格式的唯一遍历点。`ir::parse()` 将 TipTap JSON 解析为 `Vec<Block>` 序列，只遍历一次；markdown/notion/flowus/lark 四个映射层各自把 IR 渲染成平台格式，不再各自遍历 TipTap JSON。

这意味着：在 IR 层修一个 bug，一次修复四个平台同时生效；在 IR 层引入一个 bug，四个平台同时炸。72 个测试中有 13 个专门保护 IR 层的边界行为（尾部空段剥除、中间空行保留、mention 不误杀、hardBreak 保留、表格行内格式保留、嵌套列表结构保留、taskItem 勾选态保留）。

### 2.2 逐平台评分

#### Markdown（本地）—— 95 分

全要素覆盖：标题（H1-H6）、段落、有序/无序/待办列表（含嵌套）、代码块、引用、表格（GFM 语法）、分割线、行内样式（粗体/斜体/删除线/下划线/行内码/链接）。

两个小瑕疵：

- link 与粗体叠加时，`render_inlines` 中 link 匹配后立即 `break`，后续 mark 被忽略。如果用户写了一个加粗的链接文本，粗体标记会丢失。
- 下划线用 `<u>` HTML 标签兜底（Markdown 无原生下划线语法），部分渲染器（如 GitHub）不识别 HTML 标签。

#### Notion —— 90 分

annotations 完整（bold/italic/strikethrough/underline/code/link）、2000 字符自动切片（P2 已修）、表格单元格保留完整二维 rich_text 数组（P1 已修，d2d8909）、嵌套列表进 children（P2 已修）。

遗留问题：

- **代码块语言映射缺失**（P1 未修）：TipTap 的 language 值直传给 Notion，但 Notion 要求特定格式（如 `plain text` 而非 `plaintext`、`c++` 而非 `cpp`）。飞书已有 `LARK_LANG_MAP`（30 种语言），Notion 侧缺同款映射表。
- **嵌套列表递归深度无限制**（新发现）：`map_list_item` 递归构建 children 时没有深度截断，而 Notion API 单请求嵌套上限为 2 层。三层及以上的嵌套列表会触发 `validation_error`。
- **429 限流无重试**（P3 未修）：连续快速发送可能触发 Notion 的 429 限流。

#### FlowUs —— 85 分

annotations 全字段输出（含 `plain_text`、`href`、`color`），结构与 Notion 对齐。

遗留问题：

- **表格单元格多 rich_text 丢失**（新发现）：`flowus.rs` L152-158 的表格单元格映射仍用 `rt[0].clone()` 只取第一段。这正是 Notion 侧 d2d8909 已修的"多 rich_text 丢失"缺陷，FlowUs 同款未修。当单元格内文本有混合样式时（如"粗体+普通+斜体"），后续段的格式或内容会丢失。
- **嵌套列表 children 未真机验证**：代码注释标注"FlowUs 嵌套结构真机验证点；若不支持改为拍平输出"，说明该路径尚未经过真机验证。
- **429 限流无重试**。

#### 飞书 —— 75 分

亮点：原生 todo 块（block_type 17 + style.done）、原生表格走 descendant API（代码已实现，但 FEISHU-FORMAT-SPEC.md P1-2 仍写着"降级为文本"——**文档滞后于代码**）、30 种代码块语言映射表（`LARK_LANG_MAP`）、tenant_access_token 缓存。

遗留问题（FEISHU-FORMAT-SPEC.md 已记录）：

- **429/99991400 限流无重试**（P1 未修）：飞书单文档 3 并发/s、单应用 3 req/s，大文档多批次容易触发。
- **引用未使用 quote_container 嵌套**（P1 未修）：每段拆为独立 quote block，段落间失去引用归属关系。
- **text_run 无长度上限检查**（P1 未修）：飞书内部有 block 内容长度限制（经验值约 50000 字符/block），超长文本可能截断。
- **嵌套列表拍平丢层级**（P2 未修）：子列表拍平为同级 block，丢失缩进层级。
- **代码块 wrap 未设置**（P2 未修）：`style.wrap` 默认 false，长代码行不自动换行。

### 2.3 前端进站格式保真

进站（粘贴）链路已修复两个关键问题：

- **checkbox 粘贴改造**（1.2）：网页复制的待办列表（`<li><input type=checkbox>`）通过 handlePaste 预处理，标成 `data-type="taskList"` + `data-checked`，避免退化成普通列表。
- **Markdown 粘贴识别**（1.3）：`looksLikeMarkdown` 正则新增表格分隔行分支，GFM 表格能正确走 Markdown 解析。

表格仍无手动插入入口（TODO.md 已记录），但粘贴链路已通（HTML 表格和 GFM 表格均可解析）。

### 2.4 格式规范性小结

| 平台 | 评分 | 核心优势 | 最大缺口 |
|------|:---:|------|------|
| Markdown | 95 | 全要素覆盖，GFM 标准 | link+粗体叠加丢 mark |
| Notion | 90 | annotations 完整，2000 字符切片 | 代码块语言映射缺失 |
| FlowUs | 85 | annotations 全字段 | 表格单元格多 rich_text 丢失 |
| 飞书 | 75 | 原生表格+todo，语言映射表 | 限流无重试，引用无容器 |

## 三、发送速度与稳定性评估

### 3.1 已有防御机制

以下机制已在代码中实现，构成发送链路的基本盘：

**HTTP 层**：全局 `reqwest::Client` 单例（`OnceLock`），连接池 + TLS 会话复用，统一 15s 超时。飞书 `tenant_access_token` 进程内缓存 2h（提前 5min 刷新），命中时省一次认证 RTT；缓存临界区不含 `.await`，不阻塞异步线程池。

**请求编排**：Notion 目标探测用 `tokio::join!` 双路并行（db 直查 + children 拆查），不串行等待。分块追加贴合各平台上限：Notion/FlowUs 100 块/批、飞书 50 块/批、飞书表格走 descendant 单发（上限 1000 块）。

**防重发守卫**：发送按钮 `:disabled="isSending"`、快捷键 `isSending` 拦截、`doSave` 并发守卫（`saveStatus === 'saving'` 时跳过）。

**前置检查**：`navigator.onLine` 网络状态、空内容拦截（正则剥离 mention 后判空）、目标缺失时直接弹配置窗。

**错误语义**：仅 404 才降级 Page，超时/401/403 阻止发送防写错位置（v0.4.0 修复点）。Notion `create_page` 的部分失败处理：页面已建但追加失败时，错误消息附 URL 和剩余块数，用户可手动检查。

**本地保存**：`save_note` 使用原子写入（tmp + `sync_all` + rename），退出前等在途保存完成（`inFlightSave`），防 `app.exit` 截断。

### 3.2 速度瓶颈

短笔记（<50 块）典型链路 1~3 秒：本地最快（纯文件写入，毫秒级）；Notion 约 2~3 个串行 RTT（探测→建页）；飞书命中 token 缓存后约 2~4 个 RTT（token→解析文档→追加→获取 URL）。

长文场景的瓶颈集中在三处：

- **多批次串行追加**：长文每多一批多一个完整 RTT，无并行/流水线。例如 300 块的文档发 Notion，需 3 批串行追加（100 块/批），每批 15s 超时上限。
- **`resolve_target` 每次重跑**：同一目标每次发送都完整执行探测请求（Notion 双路并行 + FlowUs children 查询），不缓存结果。
- **飞书 publish 结尾多一次 GET**：`get_file_url` 仅为拿展示 URL，增加一个 RTT。

前端无批次进度反馈，长文发送时只有发送按钮 disabled + 图标旋转，体感"卡住"。

### 3.3 稳定性风险（按严重度排序）

**S1 — 全平台无重试（最大缺口）**

四个适配器的 `request()` 函数遇到 429 限流、瞬时网络抖动、5xx 服务端错误一律直接返回 Err，不重试。飞书大文档多批次天然容易触发限流（单文档 3 并发/s、单应用 3 req/s），两份格式调研文档（NOTION-FORMAT-SPEC.md §6.1 P3、FEISHU-FORMAT-SPEC.md §6.1 P1-1）都把这条列为 P1 未修。

**S2 — 无幂等/防重**

请求超时后实际状态未知（服务端可能已写入），用户重发会产生重复内容。Notion 创建页面有天然幂等性（页面 ID 不同），但追加模式（append_blocks）无请求 ID 或去重校验。

**S3 — 部分失败无定位**

Notion `create_page` 的部分失败处理得好（报"页面已创建，但 N 个块追加失败"），但 append 模式第 2 批失败时不告知"已写入几批、从哪批开始失败"，用户无法判断平台侧实际状态。飞书同样。

**S4 — 无取消机制**

发送发起后只能等完成或 15s×N 批超时。弱网下最长等待可达分钟级（300 块 × 3 批 × 15s = 45s 最差情况），用户无法中途取消。

**S5 — 前端空检查正则缺陷**

`usePlatform.ts` L76 的空检查正则 `/(?<!\S)@\S+/g` 对实例名含空格的 mention 只剥到第一个空格，残留文本使空检查误判为有内容。后端 stripMentions 后全文只剩空白 → 空 IR → 适配器兜底发出一条空内容并提示成功（"成功的空发送"）。TODO.md 已记录，严重度低（需实例名含空格且正文只有该 mention 才触发）。

**S6 — 15s 超时对弱网大批次偏紧**

单批 100 块的请求体不小（Notion 单块 JSON 约 200-500 字节，100 块约 20-50KB），弱网下 15s 可能不够。超时后又无重试，等于一次失败。

### 3.4 发送速度与稳定性小结

| 维度 | 评级 | 说明 |
|------|:---:|------|
| 短笔记速度 | A | 1~3 秒，体感流畅 |
| 长文速度 | B | 串行批次，每批一个 RTT |
| 正常网络稳定性 | A | 防重发 + 原子保存 + 错误语义严谨 |
| 弱网/限流稳定性 | C | 全平台无重试，429/5xx 直接失败 |
| 部分失败可观测性 | B | Notion create_page 好，append 模式差 |
| 幂等/防重 | D | 无请求 ID，超时后重发会重复 |

## 四、综合建议

### 4.1 格式规范性优先修复项

| 优先级 | 项目 | 平台 | 预估工作量 |
|:---:|------|------|:---:|
| P1 | FlowUs 表格单元格多 rich_text 丢失（对齐 Notion d2d8909 修复） | FlowUs | 小 |
| P1 | Notion 代码块语言映射表（参照飞书 LARK_LANG_MAP） | Notion | 小 |
| P1 | Notion 嵌套列表递归深度截断（上限 2 层） | Notion | 小 |
| P2 | 飞书引用使用 quote_container 嵌套 | 飞书 | 中 |
| P2 | 飞书嵌套列表层级保留（不拍平） | 飞书 | 中 |
| P3 | FEISHU-FORMAT-SPEC.md P1-2 更新（代码已实现原生表格，文档仍写"降级为文本"） | 文档 | 小 |

### 4.2 发送稳定性优先修复项

| 优先级 | 项目 | 影响范围 | 预估工作量 |
|:---:|------|------|:---:|
| P1 | 全平台 429/5xx 重试（读 Retry-After，最多 3 次） | 全平台 | 中 |
| P1 | 飞书限流专项（429 + 99991400 错误码识别） | 飞书 | 中 |

| P3 | 长文发送批次进度反馈 | 前端 | 中 |

### 4.3 总体评价

Sensend v0.4.0 的发送质量在"正常网络 + 短笔记"场景下表现优秀：IR 单一遍历点保障了格式一致性，72 个测试覆盖了关键边界，防重发/原子保存/错误语义等防御机制扎实。

主要短板集中在"弱网/长文/高频"场景：全平台无重试是最大缺口，部分失败可观测性不足，幂等/防重机制缺失。这些问题不影响日常使用，但在极端场景下可能导致数据丢失或重复。

格式规范性方面，Notion 和 Markdown 已接近完整，FlowUs 有表格单元格丢失的已知缺陷，飞书的原生表格实现已超前但文档未同步更新。修复 FlowUs 表格和 Notion 语言映射的工作量都很小，建议优先处理。
