逐个变体过一遍：

## **2. "中间\=排版、尾部\=光标"假设的失效场景**

**全空文档**：用户打开就发（或全删后发送）。`parse()` 返回空 `Vec`。注意这不是"误删成空列表"，而是空 IR，下游各有兜底——Notion/FlowUs 返回一个空段落块，markdown 返回 `(空笔记)`，飞书只发出一条分隔线。且前端 `publishNote` 有空文本检查（`toastError('请先输入内容')`）先行拦截，后端兜底是纯防御。链路安全，但**恰好缺一个测试锁定它**（见第 3 点）。

**用户刻意末尾留白**：会被剥。但这个产品定位是"速记→扔出去"，且三个平台对文档末尾空段落本就没有稳定的视觉语义（Notion 里末尾空段几乎不可见）。更关键的是——**剥除只发生在导出路径**，编辑器本地存的 `note.md`（TipTap JSON）不经过 `ir.rs`，用户重开窗口留白还在。所以"失效"只在导出物上，符合产品取舍，无需改。

**以非段落块结尾**：`代码块/分割线/表格 + 编辑器自动补的尾部空段` —— 空段剥除，结构块保留，正确。已有 `trailing_blank_paragraphs_trimmed`（以 taskList 结尾）覆盖同类。

**假设真正失效的场景只有一个**：用户用末尾空行做"视觉缓冲"且非常在意导出物的末尾留白。速记工具场景下这个诉求可以忽略。结论：假设成立，不需要改逻辑。

## **4. **`Inline::Mention(_) => false`** 的合理性 —— 这里有一个值得说透的发现**

**先回答行为本身**：用户把 mention 写在最后一段、后面跟了真空段 → 当前逻辑剥真空段、保留 mention 段，行为正确，不存在"该删的没删"。mention 在最尾且后面无空段 → 保留，也正确。

**但更深一层：这条规则在生产路径上其实不可达。** 调用链是：`usePlatform.ts::publishNote` 先跑 `stripMentions`（递归剔除所有 mention 节点）再 `invoke('publish_note')`。也就是说，**到达 **`ir::parse()`** 的 JSON 里永远不会有 mention 节点**。一个原本 `content=[mention, text(" ")]` 的尾部段落，到后端时已退化为 `[text(" ")]`，被判空白剥掉。

所以现状是：`Inline::Mention(_) => false` 加上 `trailing_mention_paragraph_kept` 测试，锁定的是一个**纯防御性行为**——防御"未来出现不经过 `stripMentions` 的新调用方"。这个防御方向选得对：mention 携带语义信息，误删（数据丢失）比误留（多一个块）损失大得多，四个映射层也都把 Mention 渲染成 `@label` 文本兜底。

需要修正的认知是：**别把这个测试当作"保护了真实用户场景"**。真正的保护链是前端的空检查 + `stripMentions` + 本函数的尾部剥除，三层各管一段。建议在测试注释里补一句"mention 在生产路径已被前端 stripMentions 剔除，本测试锁定防御性行为"，避免后来者误读。

顺带一个相关发现（超出本问题但同源）：前端空检查用的正则 `/(?<!\S)@\S+/g`，若实例名含空格（如 `我的 Notion`），`\S+` 只剥到第一个空格，残留文本会让"空检查"误判为有内容而放行——后端 stripMentions 后全文只剩空格 → 空 IR → 适配器兜底发出一条空内容并提示成功。不崩，但会有一次"成功的空发送"。极低频，可记入 TODO 不急着修。

---

**总结**：`parse()` 尾部剥除逻辑本身无 bug，三个方向（Text/Break/Mention）判定正确；假设在速记产品定位下成立；建议补 ①②③ 三个测试，其中"全空文档"和"mention 后空段"是真实缺口；Mention 规则合理但应注释标明其防御性质。以上仅为分析，未改动任何代码。
